# Spec: Engineering Journey v2

_Approved requirements are immutable during a run. Change this file only
following a user decision recorded in `decisions.md`._

## Goal

Ingest a user-specified span of one GitHub identity's activity (commits,
PR opens/merges, PR reviews, issue/PR comments — all public and private
repos actually contributed to) into Fulcra as durable, per-item, real
custom-typed records; build precomputed day/week/month/quarter/year
rollups and a per-period notability signal on top; and ship a
lightweight markdown narrative generator that reads that structure and
produces one paced, provenance-linked document per user-chosen range.
Ingestion/rollup math is fully deterministic; only rollup-summary text
and narrative generation invoke a model, using whatever model is
already running the task (no bundled LLM provider dependency). Deliver
as an installable, agent-agnostic skill (root-level `SKILL.md` in the
same repo as `app/`/`harness/`) whose underlying `app/` CLI also runs
standalone with no agent involved.

Full detail: see `intake/brief.md`, `architecture.md`,
`architecture-approval.md`, and `plan.md` in the deliverable repo
(`schr3b3r/engineering-journey-v2`), approved 2026-08-26. This spec is a
condensed pointer to those artifacts, not a replacement for them —
Generator/Evaluator should read the full artifacts for real
requirement/schema detail.

## Requirements

1. Backfill spans a user-specified number of years (or explicit
   start/end dates), covering all public and private repos the
   authenticated identity has contributed to (commits, PR opens/merges,
   PR reviews, issue/PR comments) — not limited to owned repos.
2. Before per-period ingestion for any repo, a cheap existence
   pre-check confirms real activity exists in that repo across the
   whole requested range, to avoid wasted API calls on org-associated
   but never-contributed-to repos.
3. Raw activity is ingested at uniform daily granularity across the
   entire requested range (not decaying/coarser for older history), one
   real Fulcra record per individual item, using the "GitHub Activity
   Raw" custom type (`MomentAnnotation` base) per `architecture.md`.
4. The backfill is safely interruptible and resumable from a durable
   Fulcra checkpoint ("GitHub Backfill Checkpoint", `DurationAnnotation`
   base), and extensible in both directions (further into the past;
   forward to pick up newer activity) without reprocessing/duplicating
   already-covered ranges.
5. "Activity Rollup" records (`DurationAnnotation` base) are
   precomputed and stored durably for day/week/month/quarter/year
   periods, with real provenance (`sources`) referencing the
   raw/lower-layer records each rollup was built from.
6. "Notability Signal" records (`NumericAnnotation` base, score in
   `value`, baseline-comparison detail in `note`) are computed per
   rollup period.
7. A markdown narrative generator asks the user for the desired range
   (full history or a sub-range), reads the relevant rollup/signal
   records, produces one paced document with a provenance appendix, and
   names the output file according to the chosen range.
8. GitHub auth defaults to the browser-based OAuth device-code flow;
   an existing `gh` session must be confirmed with the user, not
   assumed. Fulcra auth uses the existing `fulcra_client.py` pattern.
9. Every custom type's `recorded_at`, tags, and `sources` follow the
   exact per-type decisions recorded in `architecture.md` — real event
   time (never ingestion time) except where `architecture.md`
   explicitly specifies otherwise (checkpoint range), real Fulcra tags
   for every filterable dimension (`activity_type`, `repo`,
   `github_identity`, `period_type`, notability categories), not
   note-only flags.
10. Final deliverable is a root-level `SKILL.md` (sibling to `app/` and
    `harness/`) in the same repo the build harness writes to, plus a
    directly-runnable `app/` CLI with no hard agent dependency.

## Generation Rules

- Ingestion, checkpointing, and rollup/notability math are fully
  deterministic code — no model call anywhere in that path.
- Only rollup-summary text and narrative generation invoke a model, and
  only as an explicit, separate task step (the running agent performs
  the summarization/narrative step itself and writes the result back
  via a deterministic write call) — never a standalone script calling
  out to a separate bundled provider API.
- Follow `app/ENGINEERING_STANDARDS.md` (generated by the scaffold) for
  testing/type-hint/library conventions.
- Milestones are built and evaluated one at a time per
  `coordinator/milestones.md`, derived from `plan.md`'s 10 milestones —
  do not attempt multiple milestones in one Generator run.

## Evaluation Criteria

- A declared test runner exists once `app/tests/` has real test files
  (per `app/ENGINEERING_STANDARDS.md`): `cd app && python -m pytest`
  from the scaffolded venv. Evaluator must run it independently and
  report exact `test_runner: PASS|FAIL`.
- Per-milestone "Done when" criteria in `coordinator/milestones.md`
  (derived from `plan.md`) are the judged checks beyond automated
  tests — e.g. real kill/resume demonstrations, real generated output
  actually read end to end, not just "code exists."
- Regressions in already-passed milestones are in scope for every later
  milestone's evaluation, not just the current milestone's own scope.

## Out of Scope

- Multiple GitHub identities ingested in a single run (single-identity
  per run; combining identities later is explicitly a record-merge
  concern, not built here).
- Rollup recomputation once written.
- Resume-overview generation, interactive dashboards, or any output
  format beyond the lightweight markdown narrative.
- A bundled/dedicated LLM provider integration (e.g. a required Gemini
  API key for the shipped product itself — this is distinct from the
  build harness's own bundled Gemini adapter, which is likewise unused
  per `decisions.md`).
- GitHub Actions/CI activity, gists, wikis, project-board activity.
